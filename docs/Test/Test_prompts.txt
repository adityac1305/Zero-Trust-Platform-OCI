Phase 0 — one-time platform decisions, do these before deploying Keycloak (cheap now, expensive later)
1. Enable k3s secrets encryption at rest. This is an install-time flag (--secrets-encryption) in your ansible/roles/k3s/tasks/install.yaml. Keycloak's admin password will be your first genuinely sensitive secret — enable this before it exists, because turning it on afterward means migrating/re-encrypting existing secrets rather than just flipping a flag.
2. Adopt namespace-per-component as a hard rule starting now. Keycloak gets its own namespace, your auth broker gets its own, every app gets its own. Not a "nice to have later" — decide it now so it's automatic for every helmrelease.yaml/namespace.yaml you write from here on, following the same pattern you already used for cert-manager/envoy-gateway-system.
3. Write one reusable default-deny NetworkPolicy template you can drop into any new namespace folder. Takes 10 minutes now, saves a retrofit later. Apply it the moment each namespace (Keycloak's included) is created — not after.
These three are infrastructure decisions, not app decisions — do them once, correctly, and every subsequent phase inherits the benefit automatically.
Phase 1 — Identity (Keycloak)
Deploy Keycloak into its own namespace (with PSA labels + default-deny NetworkPolicy from Phase 0 applied immediately, not bolted on later). One realm for the whole platform. Create your first client here, scoped for whatever auth broker you pick in Phase 2 — don't build a real app client yet, just enough to validate login works and Keycloak itself is healthy.
Validate Keycloak in isolation before wiring anything else to it — hit its login page directly, confirm the realm/client/redirect URIs are correct. Isolating this from the ext_authz layer means when something breaks in Phase 2, you already know Keycloak isn't the cause.
Phase 2 — Authorization enforcement, centralized ext_authz (no reverse-proxy step)
Since you're skipping straight here, the auth-broker choice matters more than it would otherwise. Given the documented, unresolved oauth2-proxy/Envoy Gateway status-code mismatch I found earlier (202 vs the 200 Envoy's ext_authz protocol expects), I'd start with Authelia instead of oauth2-proxy — it has a working, documented integration pattern with Envoy Gateway's SecurityPolicy, and it does OIDC against Keycloak just as well.
If you specifically want to use oauth2-proxy anyway: do a cheap, isolated spike first — deploy it, point one SecurityPolicy at a placeholder route, and confirm the 202/200 issue actually blocks you before committing your real build to it. Better to find out in an hour than after wiring three apps to it.
Either way: own namespace, default-deny NetworkPolicy, PSA labels — same Phase 0 discipline applied.
Phase 3 — Prove the full loop against your placeholder app
Now bring in the test app (nginx/httpbin) from earlier, with its own HTTPRoute and a SecurityPolicy pointed at the Phase 2 auth broker. Validate: unauthenticated request → redirected to Keycloak → login → redirected back → straight through to app (single hop, not double-proxied). This is the point where identity + enforcement + network segmentation are all working together for the first time.
Phase 4 — Vault, migrate secrets off Helm --set
With Keycloak and your auth broker already running (and already using --set-passed secrets from GitHub Actions), deploy Vault and migrate those existing secrets to it rather than designing Vault integration in the abstract. Real secrets to migrate = a real, motivating first use case for Vault, rather than standing it up with nothing to protect yet.
Phase 5 — ongoing hardening, layered in per-app going forward
Image scanning, rate limiting on Keycloak's login endpoint, audit logging, backups — these aren't blocking anything above, so they can run in parallel or trail slightly behind, added as you bring in each real application.
